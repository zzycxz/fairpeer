## 一、先回答体积问题：会不会撑大？

### 实测基线（Windows v0.2.3）

| 项 | 实测值 | 说明 |
|---|---|---|
| CLI 静态二进制 | **103.7 MB**（已 `-s -w`） | 内嵌 pptauto 资产 40MB（`//go:embed all:pptauto`，embed.go:21）等 |
| 其中纯浪费 | pptauto 内 131 个 `.pyc` + 11,654 个 SVG | `.pyc` 运行时会重新生成，不该嵌入 |
| 桌面版前端 dist | 11 MB（嵌入 exe，main.go:39） | |
| codegraph_embed 资产 | 平台各自内嵌（repo 内 29B 占位，发布管线注入） | 不跨平台叠加 |
| uv 预捆（可选） | ~20 MB/平台（desktop-build.sh:52-58） | release.yml 目前没捆 |

### 国产化对"单个产物"的增重总账

| 增量来源 | 进哪 | 增重 | 结论 |
|---|---|---|---|
| Go 代码改动（PTY=creack/pty、镜像配置键、浏览器候选名、深链注册、启动器脚本） | 主包 | **< 1 MB（约 1%）** | 可忽略 |
| 前端改动 | 主包（嵌入 dist） | ≈ 0 | 不换框架 |
| arm64 / loong64 产物 | **独立构建产物** | 单产物不叠加 | 产物数量×3，不是体积×3 |
| WebKitGTK / GTK / gnome-keyring / libnotify / scrot / xdotool / 浏览器 / nmap / LibreOffice | **系统依赖，自带体积 0** | deb `Depends` 声明 | 由 OS 仓库提供 |
| Python 文档/PDF/PPT 依赖离线包（PyMuPDF、pdfplumber、Pillow、numpy、markitdown、python-pptx、lxml 等） | **独立能力包 docpack** | 压缩后 ~40–70 MB/架构 | 推荐默认装，但不在主包 |
| Python OCR 依赖（paddlepaddle+opencv+模型） | **独立能力包 ocrpack** | 压缩后 ~250–500 MB/架构 | 可选安装；loong64 无包（降级 pdfplumber） |

**结论：主包几乎不变肥（<1MB）。会撑大程序的唯一真凶是"离线 Python 依赖"，用能力包拆分后与主包解耦——这就是本方案的核心设计。**

### 顺手瘦身（既有膨胀，与国产化无关但应一起做）

1. pptauto 嵌入排除 `*.pyc`（embed 前清理），预计省 5–15 MB；
2. pptauto 的 40MB 文本/SVG 资产改为 zip 后嵌入、释放时解压，预计再省 15–25 MB；
3. 两项合计可让现有 103.7MB 二进制**缩 20–40MB**，抵消国产化全部代码增量还有余。

## 三、交付物体系（主包不撑大的关键设计）

```
fairpeer 主包（每架构一份）
 ├─ fairpeer 静态内核（现有 103MB 量级，国产化增量 <1MB）
 ├─ 桌面壳 + 前端 dist 11MB + codegraph 平台资产（现状不变）
 ├─ 4 个 Python 脚本源码 ~50KB（嵌入 assets/scripts，零 Go 改动）
 ├─ .desktop + 图标 + UOS info 清单 + systemd unit(rpm) <0.5MB
 └─ 依赖声明（系统库 0 自带）：libwebkit2gtk-4.0-37 等
fairpeer-docpack（可选，推荐默认，每架构一份）  ~40-70MB 压缩
 └─ 离线 wheel 集：PyMuPDF/pdfplumber/Pillow/numpy/markitdown/python-pptx/lxml/cairosvg/browser-use
fairpeer-ocrpack（可选，仅 amd64/arm64）       ~250-500MB 压缩
 └─ paddlepaddle/paddleocr/opencv + OCR 模型文件（含内网镜像安装与纯离线 zip 两种形态）
系统依赖（用户/交付工程师装）：WebKitGTK、gnome-keyring、libnotify、scrot、xdotool、xclip、poppler、nmap、(可选)LibreOffice、系统浏览器
```

设计原则（写进架构约束）：
1. **主包红线**：压缩后 ≤ 60MB（现状约 40-60MB，不破线）；任何国产化代码不得引入 >1MB 新嵌入资产。
2. **浏览器永不打包**：一律用系统浏览器（省 150–300MB）。
3. **WebKitGTK 永不打包**：系统库（省 200–400MB 的自带负担，且是其许可与安全更新语义的正确做法）。
4. **OCR 永不进主包**：能力包或内网镜像按需装。
5. **每架构独立产物**，交叉编译不乘体积；loong64 不满足的资产（codegraph/uv/OCR）一律"不内嵌 + 镜像/降级"，不为它撑大其他架构。
6. **运行时零下载为默认**（内网交付硬约束）：`[network] update_base_url`、`[runtime] uv_download_url`（照抄 codegraph download_url 模式）、pip 指向内网源或能力包。

## 六、风险与红线回顾

- 最大技术未知数仍是**老 WebKitGTK 对新前端特性的兼容**——M1 第一件事就是在真 UOS 虚机跑 GUI，一次性消除。
- 国产浏览器 CDP 能力需实测背书（探测兜底已设计）。
- KYSEC 拦截未签名子进程——签名互认证是政企交付前提，不是可选项。
- Python 版本陷阱（系统 3.7/3.8）——能力包按 系统×Python 版本 双维度预打包，绝不在线解析依赖。

## 八、Windows 应用包体积（实测 + 预测）

**实测锚点**：本机 fairpeer.exe（CLI，已 -s -w，含 pptauto 40MB）LZMA(7z mx=9) 压缩率 **22.4%**（100.6→22.5MB）；GitHub v0.2.0 发布：`fairpeer-windows-amd64.exe` = **143,649,280 B（137 MiB）**、arm64 = 127.6 MiB；codegraph v1.0.0 win-x64 zip = 43.3MB（当前 release.yml 有 `-tags codegraph_embed`；v0.2.0 产物构成反推未内嵌或内嵌较小包，两种情形都列）。

| 情形 | Windows 便携 exe (amd64) | Windows NSIS 安装器（估，LZMA 实测系数） |
|---|---|---|
| 现状（v0.2.0 实测 / 推算） | **137 MiB** | 未随版发布；不含 codegraph ≈ **28–33 MB**，若含 codegraph 内嵌 ≈ **55–65 MB** |
| 仅加国产化代码（+≤0.5MB，全部在 Linux 侧或共用小件） | ≈ 137.5 MiB | +0.1 MB |
| + pptauto 瘦身（−20~40MB 原始字节） | **97–117 MiB** | **21–27 MB** |
| + release 构建加 `-s -w`（再 −20~30MB） | **72–95 MiB** | **16–24 MB** |
| 极致：再改 codegraph 不内嵌（首用下载/内网镜像） | **~35–55 MiB** | **~10–16 MB** |

**结论**：
1. **国产化适配本身几乎不影响 Windows 包**（≤0.5MB 增量；docpack/ocrpack/WebKitGTK 都是 Linux 侧事物）——Windows 用户无感知。
2. Windows 包要变小靠的是与国产化同车交付的三件通用瘦身：pptauto 瘦身（B1 之外的 −20~40MB）、release 加 `-s -w`（B2）、codegraph 内嵌策略（B1）。全做可从 137 MiB 降到 **~72–95 MiB**（安装器 ~16–24 MB）。
3. 建议把"Windows 包 ≤ 100 MiB 便携 / ≤ 25 MB 安装器"写为主包红线（与国产化主包红线同一套预算体系）。

## 十二、CPU 架构矩阵专章（2026-09-11，三轮九代理专项调研）

### 12.1 核心新认知：龙芯是"两个世界"，不是一个架构

| | 旧世界（存量主力） | 新世界（增长方向） |
|---|---|---|
| 系统 | UOS V20 1070 loongarch64 / Kylin V10 SP1-SP3 / Loongnix 20（内核 4.19） | UOS V25 / Kylin V11 / Loongnix 25 / deepin 25（内核 6.6+） |
| dpkg 架构名 | **loongarch64**（麒麟仓库 binary-loongarch64 实证） | **loong64**（Debian 官方端口命名） |
| 上游 Go 二进制 | **无法运行**（旧世界 NSIG=128 vs 新世界 64，rt_sigprocmask 信号集大小不匹配 → 启动即段错误；ucontext 布局也不同；静态链接救不了；无任何开关可解） | ✅ 正常（内核 ≥5.19） |
| WebKitGTK | 4.0 API：Loongnix 20 = 2.26.4（低于 Wails 支持线，GUI=NO-GO） | 4.1/6.0（2.48+）✓ |
| 覆盖路径 | **龙芯自家 Go 工具链重编 CLI**（loongnix.cn Go1.26.4 abi1.0，跟版及时；x86 CI 交叉构建有先例 mihomo；**必须 GOTOOLCHAIN=local + `go mod edit -toolchain=none`**，否则自动下载上游 Go 反而在旧世界段错误/静默产错 ABI） | 现有 upstream 构建 |

UOS 商店 `info` manifest 合法 arch 值恰为旧世界命名：`amd64, arm64, mips64el, loongarch64, sw_64`（V25 时代是否接受 loong64 未验证）。WeChat 惯例=每架构一个 deb、同名同版本（control 实测：amd64/arm64/loongarch64）——与本项目一致。

**产品决策（待拍板）**：是否立项"旧世界 loongarch64 CLI"第二构建（Loongson Go 交叉编译，覆盖存量 3A5000/3A6000 政企机；GUI 旧世界明确 NO-GO，浏览器模式/TUI 兜底）。不立项则对外口径为"龙芯仅支持新世界系统（UOS V25/Kylin V11/Loongnix 25）"。

### 12.2 逐架构结论
