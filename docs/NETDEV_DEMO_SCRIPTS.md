# 网络故障定界 · 演示脚本包(P0-A 代码侧弹药)

> 用途:申报演示/录屏用两个"故障定界"场景的指令包与剧本。真机执行需靶场
> 清单在位;本文件是"照着念就能演"的脚本,不依赖现场发挥。
> 日期:2026-09-04 · 关联:`NETDEV_SPEC_V2.md` §4.11/§5.4、
> `NETDEV_AUDIT_CHAIN.md`(审计链路口径)

## 通用前置(两个场景共用,录制前逐项确认)

1. 靶场设备清单已录入运维设置(至少:1 台核心 + 2 台接入,huawei/cisco 均可),凭据走 secret store;
2. 备份已开启且至少各有一版(`立即备份`一次,或 `backup_interval` 已触发);
3. SNMP 健康轮询与告警规则已配置(设备列表的状态点有信号);
4. syslog/trap 接收器已开(场景二需要事件源);
5. 演示红线:两个场景里 AI 全程**只读 + 起草**;所有写操作(含恢复)都出现在
   变更审批卡里由人放行——这句话本身就是要演示的卖点,别跳过。

## 场景一:某 IP 失联——netdev_locate 并发定位接入端口

### 背景设定(给观众的一句话)

> "业务报 10.30.4.117 整机失联,ping 不通。传统做法是网工挨台设备登上去翻
> ARP 表;现在看平台一次问出来。"

### 指令包(复制进对话框的原句)

```
10.30.4.117 失联了,ping 不通。请定位它接在哪台设备哪个端口,判断是端口
down、VLAN/STP 问题还是终端自身问题;结论落 Finding 并附证据,拓扑上把
嫌疑段标红。
```

### 平台预期链路(每步对应观众能看到的画面)

| 步 | 动作 | 观众看到 |
|---|---|---|
| 1 | `netdev_locate("10.30.4.117")`:并发查清单内全部设备 ARP/邻居表 | 工具卡展开,逐台 `display arp \| include …` 只读命令流水 |
| 2 | 命中接入设备与端口(如 `sw-access-2 · GE0/0/17`) | locate 结果 JSON:device/interface/line |
| 3 | 对命中端口做只读核查:`display interface`、错包计数、STP/VLAN 归属 | 命令流水 + 输出;若端口 down,健康轮询状态点同步为红 |
| 4 | 画 mermaid 路径图,嫌疑段红色(`edge-bad`) | 一张路径图:核心→接入→端口✅,端口→终端❌ |
| 5 | `netdev_finding` 落结论 | 发现页新增一条,证据链 = 设备 + 命令 + 回显摘录 |

### 预期输出样例(示意)

```json
{"target":"10.30.4.117","hits":[{"device":"sw-access-2","interface":"GE0/0/17",
 "line":"10.30.4.117  4c1f-ccXX-XXXX  40  D  GE0/0/17"}],
 "covered_devices":3,"total_devices":3}
```

Finding 标题形如:`10.30.4.117 失联:接入端口 GE0/0/17 down(证据:display interface 回显)`。

### 人工对照步(增信,30 秒)

对着真机敲 `display arp | include 10.30.4.117`,与平台 locate 命中一致。

### 讲解词要点

- 传统:一台台登录翻表,10–30 分钟;平台:一次并发,命令预算/脱敏/审计全部
  在链上(审计页可回放刚才每一条只读命令)。
- ARP 未命中(IP 从未上线)是**结论**不是失败——转 DHCP 租约/MAC 路径追问,
  这句可以现场演示:`那换 MAC 地址 4c1f-… 再定位一次`。
- 收尾指给观众看:发现的证据链与审计哈希链徽标(`NETDEV_AUDIT_CHAIN.md`
  的主图取景正好在这里)。

## 场景二:变更后异常——时间轴关联锁定嫌疑变更 + 恢复提案起草

### 背景设定(给观众的一句话)

> "昨晚变更窗口动过 sw-access-3,今早它下挂两个网段不通。先别猜,把'谁改了
> 什么'和'哪里坏了'放同一条时间线上。"

### 演示前置种子(录制前完成,留 5 分钟)

1. 变更前 `立即备份` 存一版(记为 V1);
2. 走一次**真实的**变更提案(改端口 VLAN 或描述),审批执行——执行链路会
   自动产生审计写路径与执行后备份(记为 V2);
3. 人工触发可复原的"故障"信号(拔线/_shutdown 端口),让 syslog/告警规则
   命中落 Finding。

### 指令包(按顺序两句)

```
① 今早 9 点起 sw-access-3 下挂网段不通。把这台设备最近 24 小时的变更、
  告警、结论放同一条时间线,判断故障与昨晚变更是否相关。
```

```
② 对比 sw-access-3 变更前后两个备份版本,差异段就是嫌疑面;据此起草恢复到
  变更前版本的提案(restore_from 指向 V1),等我审批。
```

### 平台预期链路

| 步 | 动作 | 观众看到 |
|---|---|---|
| 1 | `NetDevTimeline(sw-access-3, 24h)`:审计写路径(变更)+ Finding + syslog/trap 同轴合并 | 日志工作台「关联源」时间线:昨晚变更条目在前,今早故障条目紧随 |
| 2 | 时间顺序 + 设备交集 → 锁定嫌疑变更 | 结论文字:"故障首现于变更后 X 小时,设备吻合" |
| 3 | 指令②:设备卡备份列表双选 V1/V2 对比 | 统一 diff,差异段即嫌疑配置面(证据一) |
| 4 | `netdev_backup(action=diff-current, id=V1)`:V1 vs 当前在跑配置 | 工具卡展开 diff-current 流水 |
| 5 | `netdev_propose(restore_from=V1)`:起草恢复步骤,每步带回滚 | 变更页新提案卡,带"↩ 恢复提案 · 来源版本 V1"标记 |
| 6 | 人工整份审批 → 执行 → `display current` 关键段回到 V1 | 执行流水 + 审计 `draft … restore-from …` 可回放 |

### 预期输出样例(示意)

时间线条目(节选):

```
09-03 23:41  change   sw-access-3  proposal-write: port GE0/0/9 vlan 30 → 40
09-03 23:52  change   sw-access-3  backup version V2 (auto)
09-04 09:07  event    sw-access-3  %LINK-3-DOWN: GE0/0/9 changed to down
09-04 09:12  finding  sw-access-3  网段 10.30.40.0/24 不可达(critical)
```

恢复提案卡:intent 形如"恢复 sw-access-3 到 V1(回退 vlan 30 迁移)",步骤
`undo` 命令 + 每步回滚,`restore_from` 显示 V1 版本号。

### 讲解词要点

- 证据链三件套:**时间轴顺序**(变更先于故障)+ **备份版本 diff**(改了什么
  的物证)+ **审计哈希链**(何时、谁放的行,不可抵赖)。
- 恢复的后半截是本平台新补的闭环:AI 只做到"对比差异 + 起草恢复步骤",
  放行权在审批卡——"AI 起草、人整份审批"是写操作的安全边界。
- 若观众问"为什么不全自动回滚":指向提案执行语义——冻结在首个失败步等人
  决策,回滚计划是随变更起草、由人按下的(B-2 无自动回滚)。

## 录屏清单(两场景共用取景)

1. 对话框贴指令 → 工具卡流水(只读命令逐条展开);
2. locate 命中 / 时间轴合并的瞬间(各场景的核心画面);
3. 备份双版本 diff + 恢复提案卡(场景二收尾);
4. 审计页哈希链徽标(绿)+ 一条 `restore-from` 审计行(全程可回放的落点)。
