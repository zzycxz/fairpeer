## 一、UX：用户喜欢什么 & 数通界面复用（需求 1.1/1.2）

### 1.1 界面原则（用户视角的"喜欢"）

运维用户喜欢的界面 = **一屏看清状态、操作路径短、危险有护栏但不啰嗦、学习成本低**。这恰好是本仓 UI 契约（NETDEV_SPEC_V2 §10）已沉淀的五条：监督在 dock（随时瞟一眼）、任务在主区、一个动作一个家、能力感知渐进披露（没配置的能力不出现灰按钮）、徽标代替常驻横幅。**结论：不新造 UX 范式，智算场景全部套用既有契约**——这同时满足 1.2（复用数通界面）。

### 1.2 数通界面同步复用（采纳，且大半已落地）

| 复用面 | 现状 | 待补 |
|---|---|---|
| 同一 shell/左 rail/dock/标题栏 | ✅ 已共用 | — |
| 设备清单：智算设备作为带 GPU 徽标的行 | ✅ 已有 | accel 类型徽标（M-1） |
| 设备卡 360 + 快捷命令 | ✅ | 机型档案徽标（E4） |
| 健康页/大屏家族 | ✅ GpuBoard 为第六屏 chip | ErrorCodeKind 泛化（M-1） |
| 对话/分诊/日志工作台 | ✅ 引擎层共用 | 推理引擎日志解析器（F3） |
| 割接形态承载部署 runbook | ✅ | 部署模板库（F1） |

**零新界面框架**：智算不是新 profile/新布局，是同一运维台里的一类设备 + 一块大屏 + 一组模板。这正是之前五轮 UI 排查守住的 §10 不变量的红利。

## 二、项目模块化（需求 1.3，核心新需求）

### 2.1 现状与差距

现状项目=视图分组，**无安全语义**：项目外设备仍可被对话触达（guardrails 全局单份）、无地址级白/黑名单、无 per-project 操作权限。用户要求的"蓝队演练/数通/智算各自独立项目 + 独立配置白名单/允许地址/拒绝地址"是真空。

### 2.2 设计：项目升为一等安全域

```toml
[[netdev.projects]]
name    = "智算一期"
type    = "aicompute"          # netdata | aicompute | blueteam（决定默认能力面与大屏默认页）
groups  = ["gpu-rack1", "gpu-rack2"]
note    = "H100×16 + 910B×8"

# —— 项目安全域（新增，全部可选；缺省=继承全局并只收严）——
[netdev.projects.allow]
addresses = ["10.1.0.0/16"]     # 允许操作的地址段（设备地址须落在内；CIDR/精确）
deny_addresses = []             # 拒绝地址（优先于 allow；堡垒/管理口保护）
commands_deny = ["rm -rf", "mkfs"]  # 命令模式拒绝表（叠加分类器，仅收严）
policy = "proposal+confirm2"    # 项目默认操作档（只许收紧于全局）
confirmers = ["张三"]            # 可选：confirm2 的合格批准人（缺省=任意人工）
```

**执行层改造点**（真正的安全语义，不是视图）：
1. 会话绑定项目（标题栏项目切换器已有）→ guardrailCheck 增加项目作用域判定：设备不在项目 groups ∨ 地址不在 allow ∨ 地址在 deny → 拒绝并审计（复用现有全局拒绝路径的先例，tools.go:117 模式）。
2. 项目发现/扫描/提案的 devices 全部先过项目域；跨项目提案直接拒绝。
3. 蓝队项目类型联动评估信封（engagement envelope）——演练项目要求信封有效才放行主动扫描档（既有闸复用）。
4. 设置页项目编辑器扩为三段式表单（基础/范围/安全域），类型决定表单预设。

### 2.3 两把锁哲学（需求 1.4，采纳用户判断）

**认同：精细 RBAC 在单机桌面场景是负资产**（学习成本 > 安全收益，且桌面无用户体系）。设计取舍：
- **默认两把锁不动**：`proposal + confirm2`（写=提案人批+危险动词二次确认），这是已验证的"简而严"。
- 精细项全部**可选且默认关闭**：confirmers 名单、变更窗口（组级已有）、deny 表、项目操作档。想管的用户能配（满足"应该让用户有权限配置"），不配就是两把锁。
- **不做**：用户账号体系、细粒度 ACL 矩阵、按命令逐条授权——明确拒绝（H 批补录）。
- 天花板拓展（跨人第二把锁）见 §五 linkpeer 四眼原则——同一哲学的多人形态。

## 三、千卡/万卡/国产卡全场景矩阵（需求 2.1-2.3）

### 3.1 六操作 × 承接方（总原则：执行归平台，治理与观测归我们）

对"部署、切割、集群切割、分配权限、检查问题、巡查状态"六操作，每厂商族的承接判定（大集群边界引用 GAPS §六 量化评估：裸机直编排 >16 节点结构性不适配 F8-F10；巡查 >30 节点需 F11/F12）：

| 操作 | NVIDIA 千卡 | 昇腾万卡 | 燧原/昆仑芯/寒武纪 | 承接机制 |
|---|---|---|---|---|
| **部署** | K8s 路径：审批 Helm/KServe manifest（k8s-apply 一步触达）✅；裸机路径=项目化模板 ≤16 节点 ✅ | MindCluster/百舸域编排；我们=部署 runbook 治理（910B 蓝本 9 步）+ MindIE/vllm-ascend 模板 | 同左（vllm-gcu/vLLM-Kunlun 模板随 M-2） | F1 模板库 + E3/E4 |
| **切割（MIG/vNPU/vGPU）** | MIG 执行归 GPU Operator MIG Manager；**切割变更走提案**（nvidia-smi mig 命令是写面）+ 切割后实例观测（nvidia-smi 已含 MIG 字段） | vNPU 归 MindCluster；同上治理 | HAMi 域（vGCU/vXPU）；我们=审批+观测 | 提案管线现成；MIG 实例进采集=triage 解析增强（P3） |
| **集群切割（资源池划分）** | K8s namespace/配额域 ⛔（拒绝清单已划） | MindX DL/Volcano vNPU 调度域 ⛔ | HAMi ⛔ | 只读观测（k8s 命名空间水位 GET） |
| **分配权限** | **两种权限要分清**：算力使用权限（K8s RBAC/配额）=平台域 ⛔；**运维操作权限=我们**（§二 项目安全域：白名单/操作档/confirmers） | 同左 | 同左 | P-1 项目模块化 |
| **检查问题** | 分诊电池 + XID/温度/显存 ✅ | 同左（错误码 catalog M-1） | efsmi/xpu-smi/cnmon 驱动 M-2 | M-1/M-2 |

### 3.2 诚实边界（写在 spec 里防止过度承诺）

- 千卡/万卡的**部署执行**（裸机逐台编排）不做——Path A（K8s/厂商集群软件）是正解，我们管 manifest 审批/验证门/回退/审计；Path B（F8-F10 裸机并行编排）仅在真实客户场景立项。
- 万卡巡查的**竞争方案并存**：厂商平台（MindCluster/百舸）自带监控，我们的差异化=**变更治理 + 证据链 + 项目安全域**，不做重复的指标大盘。
- 昇腾万卡（A3 超节点/灵衢）的部署单元是超节点不是服务器——蓝本模板按"超节点=一个 K8s 级对象"处理。

### 3.3 安全全方位（需求 2.4）

既有（已落地）：信封（主动扫描档）/审计 hash 链/estop/写档三档/脱敏全链/路径穿越校验。本 spec 新增：项目安全域（§二）/蓝队项目强制信封/跨实例四眼（§五）。补一：**智算特有的拒绝面**——模型权重文件不进 file-upload（200MB 上限即护栏，维持）；推理服务端口探活仅限本机地址（E3 的 curl -s 前缀限定）。

## 四、区块链与多 fairpeer 联动拓展（需求 3）

### 4.1 现状埋点（比你说的多一层）

linkpeersignal=LAN 内多 fairpeer 的**配对与信令层**（Ed25519 公钥交换、TTL 会话、重启即忘——PROTOCOL §10.4）；trustdomain=**本地链 + 审计链头跨锚**（AnchorAudit 已实现把 audit head 写入链式记录）。即：链的"防篡改锚"与 peer 的"身份配对"两块积木都在，缺的是把它们连起来的场景。

### 4.2 智算场景拓展（按可行性排序）

| # | 拓展 | 机制 | 可行性 | 分期 |
|---|---|---|---|---|
| L1 | **四眼原则跨实例**（最实用）：confirm2 的第二把锁由**另一台 fairpeer 的操作员**按——FDE 在客户现场起草提案，总部专家在其实例上收到确认卡（经 linkpeer 信令推送+trustdomain 身份验证），按下方生效。两把锁从"同机两步"升级为"可握在两个人手里"，且天然适配 1.4 的简锁哲学 | linkpeersignal 信令 + 提案确认请求体 + 对端 confirm UI | 高（信令层现成，加一个确认请求消息类型） | P-3a |
| L2 | **审计链互锚**：配对的 fairpeer 定期互锚对方审计链头（AnchorAudit 从本域锚扩为 peer 互锚）——多台机器互相背书，单机删改审计必被发现，无中央服务器 | trustdomain 锚记录 + peer 心跳 | 高（锚函数现成，加 peer 目标） | P-3a |
| L3 | **签名证据包**：诊断包/验收报告经本机 trustdomain 私钥签名，对方（客户/专家）实例可验签——FDE 离场件防抵赖 | 签名=链身份复用 | 中 | P-3b |
| L4 | **态势共享**：值守台+专家台同看一张 GpuBoard/同一 Finding 流 | 需要新数据同步面（linkpeersignal 只有信令） | 低-中（探索） | P-3c |

### 4.3 与智算场景的咬合

四眼跨实例恰好补上大集群的一个真空：**万卡场景里"确认"的分量极重**（一个错误 manifest 影响千卡）——单人双击的 confirm2 不够，跨实例专家确认是组织级答案；互锚则让"我们在客户环境做了什么"的审计在双方机器都有防篡改副本（合规交付件）。这两个都不需要新区块链，是既有积木的场景连接。

## 七、代码验证补记（2026-09-13，spec 落地前精读修正）

对 §二/§四 的四处关键假设做了源码精读验证，**三处需修正**：

| # | 验证点 | 代码事实 | 对方案的影响 |
|---|---|---|---|
| V1 | "会话绑定项目（切换器已有）" | **activeProject 是纯前端 localStorage 态**（netdevProjectStore.ts:10，注释自述"only the ACTIVE SELECTION is session state"）；后端零项目上下文——`NetDevTurnBegin()` 无项目参数、guardrailCheck 不感知项目、**提案无 project 字段**（findings 有，是保存时按 groups 推断） | **G-P1 改造量上调**：需新增"会话项目上下文"管道（前端切换→后端会话态→guardrail/提案/发现接线），且提案需补 project 字段（草稿创建时盖章，过滤与跨项目拒绝都靠它）。原估 ~1 周 → **~1.5-2 周** |
| V2 | confirm2 第二把锁 | `ApproveProposal(id, confirm2 bool)`——**布尔位，无任何身份概念**（谁按的不可知，审计只有"人"） | confirmers 名单需先定义"身份"：桌面无用户体系 → 身份=批准时自报 + 可选 trustdomain 密钥签名（跨实例四眼时 peer 身份自然携带）。G-P1 内含此设计 |
| V3 | "AnchorAudit 已是跨锚" | 锚定目标是**本节点 trust domain 链**（node.AnchorAudit → 本地 Propose；注释的 cross-anchor 指审计链头跨到 trust 链，**不是跨机器**）；且 linkpeersignal 仅三个配对端点（/pair/register、exchange、confirm；K 不验业务签名、两端自验），**无消息路由/relay/数据面** | **G-L2 peer 互锚是真实新增**（需 peer 间锚记录提交路径）；**G-L1 四眼确认的可行性从"高"降为"中"**——确认请求需要新数据通道（signal 服务加 relay 端点，或配对后局域网 P2P 直连——已有对方 Ed25519 公钥可加密）。L4 态势共享同依赖该通道。P-3a 估算 ~1 周 → **~2 周（含 relay/P2P 选型）** |

**净结论**：方案方向全部成立（项目安全域/两把锁哲学/六操作矩阵/linkpeer 拓展），但 G-P1 与 G-L1 的工程量各上调约一倍，根因都是"前端态/本域锚/配对信令"距"后端安全语义/跨实例通道"还差一层管道。已同步 GAPS 台账条目口径。

## 八、G-P1 开工前设计清单（开工审计补，2026-09-13）

G-P1 是下一阶段最大条目（~1.5-2 周），spec 现状=骨架（§二 TOML 草案）+ 修正（§七）。开工前需完成三项设计（ formerly "开工日细化"，升格为开工准入）：

1. **会话项目上下文载体**：候选 (a) per-tab 后端会话态（前端切换→Wails 绑定写后端，tab 级隔离，贴近现有 tab-profile 机制）vs (b) 每绑定显式传 project 参数（无状态、改动面大）。倾向 (a)；设计需定：生命周期（tab 关闭/切换）、与 `NetDevTurnBegin` 的关系（TurnBegin 是否携带项目复核）。
2. **confirmers 身份模型**（V2 修正的落地设计）：批准时自报名 + 可选 trustdomain 密钥签名；跨实例四眼时 peer 身份即签名。需定：无签名时审计如何记录（"自报：张三"）、confirmers 匹配逻辑（名单 vs 密钥指纹）。
3. **NetDevProject schema 迁移**：旧配置 projects 无 type/allow/deny——沿用 D1 软降级哲学（缺省=继承全局并只收严，加载通过+警告），不硬失败。需定：type 缺省值（推断：含 GPU 组→aicompute？不，保持 netdata 缺省+警告更诚实）。

以上三项完成前 G-P1 不开工；J4/J5 裁决同为前置。
