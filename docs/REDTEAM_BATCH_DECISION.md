> 修复、复核。红队批若立项，改变的是"打点"这一步的自动化程度。

## 一、启用门槛（附录 C 三要素，缺一不可，全部满足才存在工具面）

| 要素 | 内容 | 为什么 |
|---|---|---|
| 1. engagement 信封 | `[netdev.assessment]` 工单号/授权人/有效期/scopes——比 v1 评估模式更严（红队专用 scopes，与弱口令的分开） | 攻击动作必须可追溯到具体授权工单，到期自动回落 |
| 2. profile 级显式配置 | `[netdev.redteam] enabled = true` 逐环境显式开启 | 不存在"默认带开关"，靶场环境开、生产环境物理没有 |
| 3. 重启生效 | 开启动作本身入审计，重启后工具才注册 | 防止运行时被对话说服而开启；开启是一个"事件"而非一个参数 |

生命周期约束：engagement 到期自动回落；紧急停止覆盖红队动作；断线即停；
每一步入审计哈希链。

## 二、范围选项（拍板时选一档，不做全有全无）

| 档 | 内容 | 建议 |
|---|---|---|
| **R1 只读侦察编排扩展** | 把人工常用的只读打点前侦察（目录爆破字典编排、常见路径探测、版本指纹加深）编排化——**不含任何利用** | 最低风险；若立项建议先做这档 |
| **R2 验证类** | 已知漏洞的**无害验证**（读 banner 判版本比对 CVE 是否受影响、默认凭据单次尝试——弱口令核查已有） | 与现有弱口令核查同性质，边际风险小 |
| **R3 利用链** | payload 执行、exploit 编排（外部工具编排 msfconsole 等，产品不内置 exploit） | **风险最高**；若做，严格走"编排外部工具"路线，产品仍不内置任何利用代码；建议只在离线靶场环境开 |

## 三、无论选哪档都必须保持的边界

1. 产品永不内置 exploit/payload——只编排用户自备的外部工具（与 nmap 同哲学）
2. 永不触碰 engagement scopes 之外的资产（scopes 白名单语义复用）
3. 每一步的命令、目标、结果入审计哈希链；紧急停止即时生效
4. 红队批工具不进入 agent 默认提示词——只有信封有效时 agent 才"看得见"它们

## 四、拍板前需要回答的问题

1. 靶场训练目标是否真的需要自动打点？人工打点 + 产品侦察的教学价值是否更高（当前结论）？
2. R3 若做，编排的外部工具（如 msfconsole）授权与分发合规谁负责？
3. engagement 红队 scopes 与评估 scopes 分离的具体配置语法？
4. 审计哈希链是否需要引入第三方时间戳（防篡改升级）？

## 五、结论建议

维持当前边界（P1-3 的裁决）：**靶场阶段不立项红队批**。理由：现有闭环
（识别→修复→复核）已可完整演练；人工打点保留教学价值与证据链完整性；
R1/R2 的真实需求出现时再按本文门槛立项。
